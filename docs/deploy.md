# Deploying Formularium

The website goes on **Vercel**, the backend on **Render** (as a Docker image), the database stays on **Supabase**, and the domain and email routing are on **Cloudflare**.

| Address | What it is | Where |
|---|---|---|
| `https://formularium.dev` | the website | Vercel |
| `https://www.formularium.dev` | redirects to the line above | Vercel |
| `https://api.formularium.dev` | the backend API | Render |
| `contact@formularium.dev` | receives email, forwarded to the owner | Cloudflare Email Routing |

The website and the API share one site (`formularium.dev`), so the sign-in cookie stays first-party and works in every browser. Why it is built this way: [ADR 0010](decisions/0010-keep-own-authentication-and-harden-it.md) and [security.md](security.md).

## Before you start
You need:
- A registered domain, with mail routing working (here `formularium.dev`, on Cloudflare).
- Every migration in [`supabase/migrations`](../supabase/migrations) applied to the production database, in order and before the code that needs it (see [data-model.md](data-model.md) and [ADR 0012](decisions/0012-migrations-are-sql-files-applied-by-hand.md)).
- Your secrets to hand: the database password, the Google client ID, the Turnstile keys and the two-step encryption key. Keep them in a password manager, never in the repository.
- Everything pushed to the `main` branch on GitHub, with CI green.

## 1. Accounts
Sign up for **Render** and **Vercel** with the GitHub account that owns the repository, and let each read that repository. For an email sending provider (step 6), create an account with Brevo, Resend or a similar service.

## 2. The backend on Render
1. In Render, choose **New**, then **Blueprint**, and pick the repository. Render reads [`render.yaml`](../render.yaml) and proposes one web service, `formularium-api`, in Frankfurt.
2. Render asks for the values that are not in the file:

   | Setting | Value |
   |---|---|
   | `DATABASE_URL` | The Supabase **session pooler** address, port **5432**, in JDBC form (see `backend/.env.example`) |
   | `DATABASE_USER`, `DATABASE_PASSWORD` | The pooler user (`postgres.<project>`) and its password |
   | `AUTH_MFA_ENCRYPTION_KEY` | **The same key you use locally**, if you ever turned on two-step verification against this database. Otherwise make one (`openssl rand -base64 32`) and store it in your password manager. If it changes, every authenticator stops working. |
   | `GOOGLE_CLIENT_ID` | The OAuth client ID (never the client secret) |
   | `TURNSTILE_SECRET` | Cloudflare Turnstile secret key |
   | `BREVO_API_KEY` | A Brevo API key limited to the *Transactional email* permission (step 6). You can leave it empty for now. |

   `AUTH_JWT_SECRET` is generated by Render. The addresses and cookie settings are already in the file, as is `CLIENT_IP_HEADER=CF-Connecting-IP`, which tells the backend where to read the visitor's real address (see [security.md](security.md#running-it-checklist)). If you set variables by hand, add it too: without it every visitor shares one address, and so one set of limits.
3. Apply the Blueprint. The first build takes several minutes.
4. **Check:** open `https://<your-service>.onrender.com/api/v1/public/health`. It should answer `{"status":"ok"}`.

## 3. The API address
1. In the Render service, go to **Settings**, then **Custom Domains**, and add `api.formularium.dev`. Render shows a `CNAME` target.
2. In **Cloudflare**, open DNS for `formularium.dev` and add a `CNAME` record: name `api`, target as shown by Render, **DNS only** (grey cloud, not proxied).
3. Back in Render, verify the domain. The certificate is issued within a few minutes.
4. **Check:** `https://api.formularium.dev/api/v1/public/health` answers `ok`.

## 4. The website on Vercel
1. In Vercel, choose **Add New Project** and import the repository.
2. Set **Root Directory** to `frontend`. The framework should be detected as Vite (build `npm run build`, output `dist`).
3. Add these environment variables:

   | Variable | Value |
   |---|---|
   | `VITE_API_BASE_URL` | `https://api.formularium.dev` |
   | `VITE_SITE_URL` | `https://formularium.dev` |
   | `VITE_GOOGLE_CLIENT_ID` | The same client ID as above |
   | `VITE_TURNSTILE_SITE_KEY` | The Turnstile **site** key (the public one) |

4. Deploy. [`frontend/vercel.json`](../frontend/vercel.json) makes every page address work when opened directly or refreshed, and adds basic security headers.
5. Under **Domains**, add `formularium.dev` and `www.formularium.dev` (set `www` to redirect to the main one). In Cloudflare, add the records Vercel shows, **DNS only**.

## 5. Google and Turnstile
- **Google Cloud console**, your OAuth client: under *Authorized JavaScript origins*, add `https://formularium.dev` (keep the localhost ones for development). On the consent screen, add `formularium.dev` as an authorized domain, with `https://formularium.dev/privacy` and `https://formularium.dev/terms` as the policy links.
- **Cloudflare Turnstile**, your widget: add `formularium.dev` to its allowed hostnames.

## 6. Email that people receive
New accounts must confirm their email, so sending has to work before real users arrive. Without it the backend only writes the links to its log.
1. Pick a provider with a free plan (Brevo, Resend and similar; check the current limits) and add your domain in its dashboard.
2. The provider gives you **SPF and DKIM** records. Add them in Cloudflare DNS (DNS only). If it asks for an SPF record, merge it with the one Cloudflare created for email routing: a domain can have only one.
3. Add a starter **DMARC** record: a `TXT` record named `_dmarc` with `v=DMARC1; p=none; rua=mailto:contact@formularium.dev`.
4. In Brevo, create an **API key** (SMTP & API, then API keys) with the *Transactional email* permission set to All and everything else None, and put it into the Render setting `BREVO_API_KEY`.

   Email goes out through Brevo's HTTPS API, not SMTP, because Render's free plan blocks the SMTP ports (25, 465, 587): an SMTP attempt just times out. Leave Brevo's *authorized IP addresses* blocking off for API keys, since Render's outbound addresses change. For any other provider or host, the backend also speaks SMTP (`MAIL_HOST`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_PORT`), used only when `BREVO_API_KEY` is empty.

## 7. Check it end to end
1. Open `https://formularium.dev`, then refresh on an inner page such as `/learn` (no 404).
2. Create an account. The confirmation email arrives (check spam the first time) and its link signs you in.
3. Sign in, reload the page: you stay signed in. Sign out, then in with Google.
4. Turn on two-step verification in Settings, sign out, and sign in with a code.
5. Save a formula, make a PDF, and send a password-reset email to yourself.
6. Work through the checklist in [security.md](security.md#running-it-checklist), in particular the real client address behind Render's proxy.

## Free-plan limits
- A free Render service **sleeps after about 15 minutes without requests**, so the first request after a pause can take 30 to 60 seconds. The website retries by itself, but it will feel slow. A paid plan, or a regular ping, avoids it.
- The Supabase free database **pauses after a week without use** and has to be resumed from its dashboard.
- Render builds from `main` on every push. CI runs the tests on the same push, so check it is green first.

## Rolling back
In Render, open **Deploys** and redeploy an earlier one. In Vercel, **Deployments** has the same option. Database migrations are not rolled back this way: write a new migration instead.
